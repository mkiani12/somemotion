Facts the proposal is built on (all read in the DDL or the legacy code, file references in §6):
- **Only `TVideoDailyFilterable` holds visit dimensions.** Milestones, downloads, durations, startup, buffer time and the
  identification of a video live in `TVideoDaily`, which has video and page only. So "video measures on every query"
  needs a measure × dimension matrix (the `AnalyticsVideoMeasures` description): a dimension a measure's source lacks
  is refused by name; video never falls back to raw (owner 2026-09-26: rollups only, no realtime).
- **`Users` in both video rollups counts any video event, impressions included** — legacy's unique users (2026-10-04,
  "kept, documented": on impression-heavy videos users can exceed plays). `TVideoUserSessionsDaily` counts starters
  exactly, but by video and user only. Picking both would break engine rule 1 (G4-Q7; the owner's #56, any event makes a
  realtime user, is the likely answer but rules another context).
- **Server-side purchases carry the store's user agent, not the shopper's** (spec sub-project 6 §4.7: until the
  collector honours `ar.c_ip` / `c_ua` for mode 110). On production the connector also sends `add_to_cart` and
  `begin_checkout` from the server (`Trust = 2`, fleet probe 2026-10-26), so today **every** commerce row is a
  server row. Commerce × device or channel needs a join by client id (G4-Q3).
- **Every exchange property is a string**, `amount` included; the event is `gifcard` (sic); `screen_viewed`,
  `limit_order_placed`, `price_alert_set` are in no pack (registry seed `1d7d33f6…`).
- **No video event carries a content category**; `video_seeked` (with from/to positions), volume, subtitle,
  fullscreen and intro-skip events exist in the registry but no rollup holds them.

## 2. The proposal in one page

- **Measures:** `AnalyticsMeasures.video { … }` (35 fields: plays, impressions, watch time, completion, milestones,
  health, rebuffering, startup, quality drops, ad breaks) and `AnalyticsMeasures.commerce { … }` (44 fields: orders and
  money in one currency, buyers, the buying-path users, product units and revenue, carts, order states, coupons,
  reviews, downloads, searcher conversion); top-level `searches`, `zeroResultSearches`, `zeroResultSearchRate` (site
  search is the canonical pack, not commerce). Each has its change mirror and an `AnalyticsMeasure` value for sort and
  `having`.
- **Dimensions:** `VIDEO`, `PLAYBACK_SOURCE`, `VIDEO_QUALITY`, `AD_POSITION`, `ISP`, `PRODUCT`, `PRODUCT_CATEGORY`,
  `PAYMENT_METHOD`, `COUPON`, `SEARCH_TERM`, `RATING`, and for exchange `COIN`, `FAILURE_REASON`, `EVENT_STATUS`.
- **Queries:** `analyticsVideos(groupBy: VIDEO | PLAYBACK_SOURCE | QUALITY | QUALITY_DROP | AD_POSITION | ISP)` and
  `analyticsCommerce(groupBy: PRODUCT | PRODUCT_CATEGORY | PAYMENT_METHOD | COUPON | SEARCH_TERM | RATING)`, both on the
  approved breakdown input (no paging, F-11). The catalogue goes from 14 queries to 16.
- **Input:** an optional `currency` on the traffic, series, breakdown and activity inputs.
- **Exchange:** no new query and no sub-object (G4-Q4).
- **Everything else reuses groups 1–3:** completion by channel is `analyticsReferrers(groupBy: CHANNEL)` selecting
  `video { sessionCompletionRate playSessions }` with `having VIDEO_PLAY_SESSIONS ≥ 100`; the user environment is
  `analyticsDevices` with `video { users bufferRate }`; the sales heatmap is `analyticsActivityPattern` with
  `commerce { orders }`; the videos table sorts by any `VIDEO_*` measure.

### G4-Q1 — One measure vocabulary on every query (recommendation 1)

**Ruled 2026-10-27 (decision #61): yes, as recommended.**

**Question.** Do video and commerce measures become sub-objects of `AnalyticsMeasures`, selectable on every query, each
served from the one source that defines it and refused by name where that source lacks the dimension asked for?

**Example.** Completion by channel (VD-16, legacy `VideoChannelCompletionQueryBuilder`) becomes
`analyticsReferrers(groupBy: CHANNEL, having: [VIDEO_PLAY_SESSIONS ≥ 100]) { rows { key measures { video {
sessionCompletionRate playSessions } } } }`: no video-specific channel reader. But `video.videos` under a `DEVICE_TYPE`
filter is refused (`measure-not-available-for-dimension`): only `TVideoDaily` knows which ids are real videos, and it
has no device column.

**Recommendation.** Yes, with two engine rules stated in the contract:
1. one source per measure, never a second one (engine rule 1);
2. in a breakdown, the rows are the keys of the **sort measure's** family. Another family's measures are read for
   those keys only (the Q5 `url` pattern).

**What it changes.** Two queries instead of a video and a commerce reader per card (legacy has 17 video and 13
commerce query builders). Every group-2/3 query gains the sub-objects. The front team composes cards from the existing
breakdowns. The video rollups are daily, so the existing rulings for daily sources apply to every video read: the
window snaps to whole UTC days and is echoed (G2-1, #15), and video series are UTC-day buckets (Q-P3). A call mixing
video measures with the half-hourly traffic measures is therefore refused by name (`mixed-window-grain`), so that no
number depends on what else was selected (F-1); the client makes two calls. Commerce reads raw, so it keeps hours and
the reader's zone.

**Alternatives.**
- (a) Dedicated `analyticsVideos` / `analyticsCommerce` only, each with its own dimension list. This re-declares
  channel, device, location and campaign groupings that the six breakdowns already define, and the definitions can
  drift (ADR-0068's defect class #254–#258).
- (b) Fall back to raw `Records` where a rollup lacks the column. This breaks the 2026-09-26 rollups-only ruling, at
  ≈ 98 M video events a day fleet-wide.

### G4-Q2 — Money: one currency per query (recommendation 4)

**Question.** Commerce money is summed in one currency per query: the input's `currency`, or by default the window's
most common verified purchase currency (D5), never converted. What happens to orders in other currencies?

**Example.** The e-commerce hero shows "29.4M T" (wireframe v5). If a store sold 120 orders in `IRT` and 3 in `USD`
in the window, the recommended answer is:
- `currency: "IRT"`, `orders: 120`;
- revenue and AOV over those 120 only;
- `otherCurrencyOrders: 3`, so the page can say "3 orders in other currencies not included".

Today the case is hypothetical: the fleet probe found one sender and one currency (`IRT`, 19 verified purchases in 90
days). The rule decides what a multi-currency store will see, at no cost to the single-currency case.

**No customer data yet.** This defines numbers for data no customer sends: the only commerce sender is our dogfood store, in one currency (fleet probe 2026-10-26). **It can wait** for the first real store. Every option gives the same numbers for a single-currency store, and the multi-currency case is cheaper to rule on a real store's currency spread. Ruling now only fixes the shape (`currency` input, `otherCurrencyOrders`) before slice 14 starts.

**Recommendation.**
- Orders, buyers and every money field count the chosen currency only, so AOV = revenue ÷ orders always holds.
- `otherCurrencyOrders` exposes the rest.
- A `change` across two windows whose default currencies differ is null.
- Amounts are `Float`, as stored (`Records.Value` is Float64), unscaled. The "M T" display scaling moves to the client
  (legacy scales on the server, spec §4.2a).

**What it changes.** The `currency` input on four inputs. `commerce.currency` and `otherCurrencyOrders` on the
measures.

**Alternatives.**
- (a) Money as a list per currency (`revenue: [{currency, amount}]`). This is exact, but every money card must handle
  several values, and sort and `having` on money become ambiguous.
- (b) Convert to one currency. This needs an exchange-rate source and a rate date per order, neither of which exists.
  The owner ruled it out (D5).
- (c) Count orders in all currencies and money in one. AOV then mixes populations; legacy hit exactly this and fixed it
  ("AOV per same-currency orders", 2026-10-10).

### G4-Q3 — Commerce × visit data: conversion rate, device, channel

**Question.** A verified purchase arrives from the store's server: it carries the shopper's client id, but the
store's user agent and no session referrer (spec §4.7). How are conversion rate (EC-6), mobile vs desktop (EC-12),
revenue by channel (EC-16), searcher conversion (EC-23) and time to purchase (EC-19) defined?

**Example.** "Purchase CVR" on the KPI row is legacy's always-0 card. Session-scoped (purchases ÷ sessions) needs the
purchase's browser session, which the server event does not carry. User-scoped (buyers ÷ users) joins on
`CidUserChecksum`, which it does carry. On production every commerce row today is a server row: the connector sends
`add_to_cart` and `begin_checkout` with `Trust = 2` too (fleet probe). On `mVnpUBvRvwwn` every commerce row has a
browser user agent and none has a session referrer, browser rows included (per-project probe). Whether a server row's
user agent is the shopper's or the store's is still open: compare `UaBrowserName` / `UaOSName` of `Trust = 2` and
`Trust = 1` rows of the same users (one statement, offered to the team lead).

**No customer data yet.** This defines numbers for data no customer sends (only the dogfood store, every row from its server). **It can wait, and should**: whether a real store's rows carry the shopper's browser and referrer (project statement 5) and how large the client-id join is are both measured best on a real store. The collector change (P10) is the one part worth doing early, because it is useful without any ruling.

**Recommendation.**
1. Define conversion as **user-scoped**: `conversionRate = buyers ÷ users` of the same population, and likewise
   searcher conversion. The denominator `users` counts users with **any event**, as every user count does (G-1) and
   as the owner ruled for realtime (#56); the owner confirms it for conversion.
2. **Fix the dimensions at the source:** the collector stamps the shopper's IP and user agent that the connector
   forwards (seed P10, `ar.c_ip` / `c_ua`), so a purchase row carries device and location like any hit.
3. Until then, refuse visit dimensions on server-side measures by name.
4. Channel for a purchase = the buyer's session referrer, read from the buyer's browser rows by client id within the
   raw span cap (a last-touch session before the purchase), as a separate cost-gated item.
5. Leave time to purchase out until the session start exists.

**What it changes.**
- `conversionRate` and `searcherConversionRate` are defined.
- EC-12 and EC-16 are served once P10 ships (device, location) and once the join is built (channel).
- Until then they are refused, not zero.

**Alternatives.**
- (a) A session-scoped CVR. This needs the connector to send the browser session id, which is a plugin and identity
  change (spec/identity.md §5 reads only `sh_std`).
- (b) A per-request client-id join for every visit dimension. This is a raw join of the commerce rows with the browser
  rows on every request; on a large store the cost is unknown, and the join must pick which session gets the credit.

### G4-Q4 — Exchange: the approved event queries, not an `exchange { }` sub-object (recommendation 5, different shape)

**Question.** Recommendation 5 says to contract exchange from the registry's 37-event pack. Should that be a measure
sub-object (`exchange { signUps kycApproved firstTraders … }`) or the approved event queries plus three event-property
dimensions?

**Example.** The activation funnel (EX-1) becomes
`analyticsEvents(filters: [EVENT_NAME IN [sign_up, login, kyc_approved, first_deposit, first_trade]]) { rows { key
measures { users } } }`: users per step, each step counted alone, which is exactly how the commerce buying path is
defined (spec §4.2). Deposits by asset (EX-5) are the same query with `secondary: COIN`. Trader yield per channel (EX-3)
is `analyticsReferrers(groupBy: CHANNEL, secondary: EVENT_NAME)`. **No site sends exchange events** (fleet probe
2026-10-26: none since 2026-10-11 in the rollup, none valid or invalid in raw on 2026-10-24).

**No customer data yet.** No project sends exchange events, valid or not (fleet probe 2026-10-26). **It can wait** for the first exchange that sends: the recommendation adds no query, so nothing is lost by waiting, and real events would show which properties (asset, status, failure reason) are actually populated. Ruling now costs only a review.

**Recommendation.** The event queries, with `COIN`, `FAILURE_REASON` and `EVENT_STATUS` added as dimensions.
- Every exchange screen number that is a count or a user count of an event is served this way.
- The rest are per-user cohorts or distributions, not exchange-specific: time to first trade, repeat-trader rate,
  trade-count distribution, decay curve, retention cohorts and reactivation. They go to G4-Q10.
- Screen usage and feature adoption name events the pack does not have, so they are outside.

**What it changes.** No new query and no 30-field sub-object built against zero data. `screens/exchange.graphql` shows
the calls.

**Alternatives.**
- (a) The `exchange { }` sub-object. That is about 30 fields, each marked "no site sends it yet". The engine slice
  would build and test against synthetic data only, and every field duplicates `events` / `users` filtered to one event
  name: two definitions of one number.
- (b) Defer exchange entirely until a sender exists. That is cheapest now, but the page then has no contract at all,
  while the event queries already serve most of it at no extra cost.

### G4-Q5 — `VIDEO_PLACEMENT`: a dimension, or content only (recommendation 2)

**Question.** Recommendation 2 adds a `VIDEO_PLACEMENT` dimension, content by default. The owner ruled on 2026-09-26
that banner ad units are excluded and "there is no ad view". Should ad units be queryable at all?

**Example.** Fleet, 2026-10-11 … 10-25: 1,214,288,985 ad-unit events (72 projects) against 92,790,335 content events
(114 projects), so 93 % of all video events are ad units. On `UKRlSkNOScQA` that is 12,965,156 ad-unit starts against
76,570 content starts.

**Recommendation.** No dimension now. Every video measure is content-only by definition, and ad breaks stay readable
through the `ad*` fields.

**What it changes.** One enum value fewer. It is additive later, so an ad-unit view can add `VIDEO_PLACEMENT` without
breaking anything.

**Alternative.** The dimension now, content by default. One extra filter term on every video read, plus a public way
to read the 93 % that the owner said the dashboard does not show. The ad-blocking phase may also stop collecting those
events.

### G4-Q6 — Search visibility belongs to the SEO module (recommendation 2)

**Question.** VD-4…6 (the organic discovery funnel, index and schema health, queries driving plays) join video plays to
Search Console data. Are they part of SEO's published language rather than an analytics query?

**Example.** Legacy's band reads `SearchConsoleData`, `DiscoverData` and `SearchConsoleDataWithQuery` on the GSC
cluster, and estimates plays per query as page plays × query clicks ÷ page clicks (`VideoSearchVisibility.js`). The
analytics half is only "plays whose session came from Google search, per page", which is `analyticsVideos` /
`analyticsPages` with a `REFERRER_SOURCE` filter.

**Recommendation.** Yes. The SEO module (the SEO parity pass) owns the GSC join and the estimate. Analytics serves
plays by referrer.

**What it changes.** VD-4…6 are outside here and land in SEO's contract.

**Alternative.** An analytics query that reads GSC. That puts a second published language (Search Console data, its
plan gate, its estimates) into the analytics catalogue.

### G4-Q7 — Video `users`: any video event, or players only

**Likely answer: #56** (owner, 2026-10-26: any event makes a realtime user online). Read for video, that is "any video
event, impressions included", the recommendation below. #56 rules the realtime stream, a different context, so the
owner confirms; it is a short confirmation, not an open design question.

**Question.** `video.users` is "distinct users with any video event, impressions included" (legacy, 2026-10-04). The
wireframes label it "unique viewers / users who watched". Which definition?

**Example.** On an autoplay or impression-heavy video, users can exceed plays; legacy documented this and kept it. The
user-environment card (VD-20) and the detail panel's unique users (VD-28) both show this number.

**Recommendation.** Keep "any video event" for now, because it is the only user state every video rollup holds, so
one definition can be served on every dimension (rule 1). Propose a `StartedUsers` state on `TVideoDailyFilterable`
(an additive column and view change) if the owner wants "users who played".

**What it changes.** The field's definition, and possibly an archive proposal.

**Alternative.** "Users who played" now. That is servable only by video (`TVideoUserSessionsDaily`), not by device,
channel or location, so the user-environment card would be refused until the archive change ships.

### G4-Q8 — Average completion — **withdrawn, no decision needed**

The question rested on legacy's section inventory (`P5-SECTION-INVENTORY.md`), which is out of date: legacy's overview
ring now uses the PRD definition (`VideoOverviewRealReport.js` 168–180, `VideoSummaryQueryBuilder.js` 71–73), the same
as the detail panel. `avgCompletion` takes it: watch time ÷ (plays × length) over plays of videos with a known length,
capped at 1, null when none has one. Duration coverage (project statement 4) only says how many plays the number
covers. The original text follows for the record.

**Question (withdrawn).** Legacy has two definitions of one number:
- the overview's ring is milestones passed × 25 % ÷ plays;
- the detail panel is watch time ÷ length over plays that reported a length.

Which one is `avgCompletion`?

**Example.** In the archive check of 2026-09-26, only 9.7 % of content rollup rows carried `video_duration`, so the
duration-based number covers few plays. The estimator reads low by up to a quarter per play. Duration coverage since
the identity release is now known: 91.2 % of plays on `CHyjot2edlsQ` and 99.9 % on `pPUsRuZitL3f` carry a length
(per-project probe 2026-10-26), so the duration definition covers almost every play.

**Recommendation.** One definition: watch time ÷ length over plays with a length, null when none has one, if the probe
shows most plays now carry a length. Otherwise the estimator, labelled as such. Either way, one field.

**What it changes.** The ring and the panel then show the same number.

**Alternative.** Two fields (`avgCompletion`, `avgCompletionEstimate`). Exact, but a customer sees two completion
numbers for one video.

### G4-Q9 — First purchase: the store's flag or a read-time derivation (events are stateless)

**Question.** `purchase.is_first_purchase` (and the exchange events `first_deposit`, `first_trade`) are state the site
computes. Under "events are stateless" (2026-10-25), are they facts of the moment to keep, or derived values to
recompute at read time?

**Example.** The first-time buyer share (EC-20) and the repeat rate (legacy: 1 − that share). A read-time derivation
("no earlier verified purchase by this client id") only sees Shahin's own history: `Records` keeps at least 512 days
and starts at the install, so a customer with 30 orders before the install reads as first-time.

**No customer data yet.** `is_first_purchase` has been sent only by the dogfood store, and `first_deposit` / `first_trade` by nobody. **It can wait** for the first real store; the cost of waiting is nil.

**Recommendation.** Keep the store's flag. The ruling targets state the SDK keeps in its own memory (`from_quality`);
"this is the customer's first order" is a fact the store knows at that moment, from its full order book.

**What it changes.** `firstTimeBuyerShare` stays on the flag. The repeat rate stays 1 − share until G4-Q10, labelled
"orders from returning customers" (a share of orders), never "customers who bought more than once" (a share of
customers, which needs G4-Q10's per-user read): decision #103–#107 (issue #460), owner ruling pending.

**Alternative.** Derive at read time. Wrong for every customer older than the install, and a raw scan per request.

### G4-Q10 — Per-user cohorts and distributions: a later generic query

**Question.** Several items need per-user reads: retention cohorts, repeat purchase and repeat trader rate, time to
first trade, trade-count distribution, decay curve, reactivation, at-risk customers. Are they out of group 4, to come
back as one generic cohort query?

**Example.** The exchange retention heatmap (XW-42: first-trade month × D1/D7/D30/D90) and the e-commerce repeat
purchase rate (EW-36: week-1 return over 3/6/12 months) are the same question about different events.

**Mostly no customer data yet.** The commerce and exchange cohorts concern data no customer sends. **It can wait** for the first real store or exchange; the generic cohort query would then be designed and cost-gated on real events (it would also serve video and pageview retention, which do have data).

**Recommendation.** Out of group 4. When the first real store or exchange sends data, propose one
`analyticsRetention` / `analyticsUserDistribution` pair over any event, cost-gated.

**What it changes.** Those items are outside in `coverage.json` with this reason.

**Alternative.** Pack-specific cohort fields now. These are three implementations of one idea with no data to test
them on.

### G4-Q11 — In-player interactions, seek heatmap, playback speed: a rollup, or outside

**Question.** VD-31 (interactions, seek heatmap) was "not collectable" in legacy. The registry now has `video_seeked`
(from/to positions required), volume, subtitle, fullscreen, intro-skip and rate-change events, but no rollup holds
them, and video reads rollups only. Should an archive rollup be proposed, or should they stay outside?

**Example.** The playback-speed mix (VW-84) and "subtitles on" (VW-96) need `playback_rate` and `subtitle_enabled`.
On production they almost never differ: 12 of 69,135 heartbeats (`CHyjot2edlsQ`) and 51 of 1,221,269
(`pPUsRuZitL3f`) run at a rate other than 1×, and no event has subtitles on (per-project probe, one day). Seeks are
real: 3,360 and 183,852 `video_seeked` events that day, every one with a playback id.

**Recommendation.** Outside for now: the speed and subtitle cards would show ≈ 0 % today. Propose a small
`TVideoInteractionsDaily` (day × video × action × 5 % position bucket) for the seek heatmap when the detail-panel slice
is built.

**What it changes.** VD-31, VW-84 and part of VW-96 stay outside.

**Alternative.** Propose the rollup now: an archive change (additive, reviewed) for a panel nobody uses yet.

### G4-Q12 — Windows that start before a source existed

**Question.** Video data starts 2026-09-25 15:00 UTC (ad breaks and playbacks backfilled to that day), quality events
on 2026-10-26, and the 400-day TTLs end some sources at the other edge. What does a measure return for a window that its source only
partly covers?

**Example.** A "last 3 months" range today starts 2026-07-26, two months before any video row. Legacy sums what
exists, and its deltas are null when the previous window starts before collection. A `PREVIOUS_YEAR` comparison of
ad breaks never has data.

**Recommendation.**
- The current window reads what the source holds.
- `previous` and `change` are null when the comparison window starts before the measure's source.
- Both are documented per source (the `SOURCE_FROM` mechanism the page slices use).
- No refusal, because a refusal would break the 3-, 6- and 12-month presets for months.

**What it changes.** A documented rule, with no field added.

**Alternative.** Refuse by name (`RANGE_BEFORE_DATA`), as pages do before `DATA_FROM` (#26). That is exact, but the
default presets fail until 2027.

### G4-Q13 — Commerce source: raw `Records` now, a rollup later

**Question.** D1 (2026-10-09) chose raw reads because the archive was hands-off. Since 2026-10-14 additive tables are
allowed after review. Should a commerce rollup be proposed now?

**Example.** The PREWHERE bench passed (products 0.69 s / 345 MiB cold over 30 days on a 362 M-row project), but it ran
with no real store data, and the fleet probe found 19 verified orders in 90 days, all from the dogfood store. The
contract is the same either way.

**No customer data yet.** 19 verified orders in 90 days fleet-wide, all from the dogfood store. **It can wait**; by its own recommendation the decision is taken on a real store's cost-gate numbers.

**Recommendation.** Stay raw. Propose a rollup only when a store's orders make a statement fail the cost gate (2 s,
5 GB at 30 days, spec §4.5).

**What it changes.** Nothing in the contract; slice 14 measures it.

**Alternative.** A rollup now. That is an archive change and a backfill for one dogfood store.

## 5. Costs and gaps the slices carry (recorded, not decisions)

1. **Carrier names.** `ISP` keys are GeoIP autonomous-system organisation names, not carrier brands. The design's
   "Irancell / MCI / TCI" needs a curated organisation → carrier map, as legacy noted. This is the same pattern as
   `botKind`. **Ruled out (owner 2026-11-17, issue #705):** Shahin is an international product, so the provider is
   shown by its real GeoIP organisation name; a curated, single-country carrier list is not served (!1964 reverted).
2. **The video identity key.** Pre-release rows hash `cutQueryStringAndFragment(VideoKey)`; post-release rows hash
   `video_id`. Only `TVideoDaily` holds `VideoIdSource`, so a `VIDEO` filter on the other rollups is exact for
   post-release rows only. This is legacy's "legacy group" rule. It shrinks as pre-release data ages out.
3. **The playbacks rollup has no video id.** `errorRate` and `exitBeforeStartRate` are site-level only; per video they
   are refused (VW-63).
4. **Startup percentiles (VW-58)** need a distribution; the rollup holds a sum and a count, so only the mean is served.
5. **Commerce order states** (unfinished, failed, on-hold) need the latest status per order: an `argMax` over
   `order_status_changed` per request. The pending value of on-hold orders (EW-20, EW-73) needs an amount the
   connector does not send (spec §4.7). The payment failure rate (EC-8, EC-9) reads the same per-order pass:
   online-gateway orders never paid ÷ online-gateway orders (decision #103–#107 (issue #460), owner ruling pending). Legacy
   divides orders that **ever** failed by **all** orders, cash on delivery included, under a label promising "never
   paid"; wireframes EW-19 and EW-34 give two more definitions.
6. **`view_item`, `view_item_list` and `select_item` read 0** until production's `EVENT_PACKS` includes `commerce`
   (owner deploy decision).
7. **The rule-1 check for video:** `TVideoDaily` and `TVideoDailyFilterable` must hold the same starts, completions,
   impressions and heartbeats per placement as raw `Records`. **Verified on production** (2026-10-25, all 8 cells equal
   on `CHyjot2edlsQ` and `pPUsRuZitL3f`) and on R0 (`r0parity001`, 2026-09-27: 13 / 13 / 13). The slice keeps the check
   as a verify script.
8. **Event-property dimensions read raw.** `COIN`, `FAILURE_REASON` and `EVENT_STATUS` live in `Props`, which the
   event rollups do not hold: an `analyticsEvents` call with one of them as a filter or `secondary` reads raw `Records`
   within the 93-day cap (the Q3 precedent), with the explicit `PREWHERE EventName … AND Mode = 110` (spec §4.5).
9. **`ISP` on non-video measures reads raw** within the span caps (G2-Q8): no traffic rollup holds the ASN column.
10. **Deltas change on the video page.** Legacy's video page gives a relative % change even on rate cards
    (`VideoOverviewRealReport.js` 113–116; only the environment share change is in points); F-3 gives rates in points.
    E-commerce legacy already uses points. A changelog note for the video page.
11. **Completion per playback source.** 20.8 % (`CHyjot2edlsQ`) and 11.6 % (`pPUsRuZitL3f`) of completion events carry
    no playback source today (30 days), so `completionRate` split by `PLAYBACK_SOURCE` would undercount. The contract
    therefore adds `playbackCompletionRate` (completed ÷ started playbacks, `TVideoPlaybacksDaily`, the source taken
    from the start), which is legacy's method, and serves VD-13 with it; `completionRate` is not split by source.
12. **Rendition labels are verbatim.** Players report the height they decode (`362p`, `722p`, `1081p`, `2276p` on
    `pPUsRuZitL3f`), and an unknown rendition is 69 % of watch time on `CHyjot2edlsQ` (Chakavak's bridge reports none).
    `QUALITY` rows return the labels as stored; legacy drops `''`, `unknown` and `0p` from the shares. Whether to fold
    labels onto a standard ladder (360/480/720/1080) is a display choice the slice records with the legacy comparison.
13. **Carrier names.** The three largest providers on both video projects are MCI ("Mobile Communication Company of
    Iran PLC"), TCI ("Iran Telecommunication Company PJS") and Irancell ("Iran Cell Service and Communication
    Company"): the curated map (item 1) is short.
14. **Orders in other currencies.** Legacy counts orders in all currencies but money in one (`EcommerceRealData.js`
    142–149); under G4-Q2 orders count the chosen currency only, with `otherCurrencyOrders` beside them.
15. **The data map is out of date on legacy's video page** (legacy survey 2026-10-26): VD-3 is absent from the response,
    not null; VD-9, VD-11 and VD-21 are computed (VD-21 in points), not pending; VD-14's last step is `video_completed`;
    VD-29 fills the ISO duration; VD-5 is null only without a post-release page. The census should be corrected when
    slice 13 starts.
16. **G3-9 and the `events-*` wireframes.** `events-video` and `events-vod` are mock designs with no front-cp page.
   Whether they become typed screens or chart-engine dashboards (G3-9) is a front decision; their numbers map to the
   same measures either way.
17. **Session completion is ÷ sessions with a play** (decision #101 (issue #457)). `sessionCompletionRate` (VD-10, VD-16,
    VW-37) divides by the sessions that played a video, as legacy does (`VideoChannelCompletionQueryBuilder.js` 15–21);
    the legacy copy and wireframe VW-28 say "÷ all sessions". The number stays; the label is corrected. Example: 1,000
    sessions, 200 with a play, 50 with a completion: the card shows 25 %, not 5 %.
